## 1. Sit-to-Stand Check

**Source files:** `lib/assessments/sitToStand.ts`, `app/assess/sit-to-stand/page.tsx`, `lib/i18n/en.ts` (`assess.sitToStand`)

1. **Raw measure:** `reps` — count of full chair stands completed in a fixed 30-second timer. No cap on the rep count itself; the *timer* is fixed at 30s (not a score cap, a test-duration limit). Age is collected as a raw number (stepper input, floored at 50 — see below), not a pre-selected band.

2. **Cut-off table (as coded, `NORMS` in `sitToStand.ts`, updated to the full published set of Rikli & Jones (1999) 5-year bands):**

   | Sex | Age band | Range (stands/30s) |
   |---|---|---|
   | Female | 60–64 | 12–17 |
   | Female | 65–69 | 11–16 |
   | Female | 70–74 | 10–15 |
   | Female | 75–79 | 10–15 |
   | Female | 80–84 | 9–14 |
   | Female | 85–89 | 8–13 |
   | Female | 90–94 | 4–11 |
   | Male | 60–64 | 14–19 |
   | Male | 65–69 | 12–18 |
   | Male | 70–74 | 12–17 |
   | Male | 75–79 | 11–17 |
   | Male | 80–84 | 10–15 |
   | Male | 85–89 | 8–14 |
   | Male | 90–94 | 7–12 |

   `ageBand(age)` maps a raw age to one of these seven bands, clamping at the 90–94 ceiling for any age above it (no extrapolation past the study's own range). **There is no published 50–59 band** — confirmed against the primary source and cross-checked against multiple independent reproductions of the same table: Rikli & Jones's own normative study (N=7,183) is titled *"...Community-Residing Older Adults, Ages 60–94."* Rather than invent one, ages 50–59 are deliberately scored against the 60–64 band — the youngest real data available, and a conservative choice, since scoring below an older cohort's typical range is if anything a stronger signal for a younger person, not a weaker one. The age input in `app/assess/sit-to-stand/page.tsx` is floored at 50 to match (this is a 50+ product), not left open to any age. Result is `below` if `score < lo`, `above` if `score > hi`, else `within`.

   *(Prior state, now fixed: this table previously had only three coarse points — `AgeBand = 60 | 70 | 80` — selected via three buttons in the UI labelled "60–69" / "70–79" / "80+". That meant, for example, a 68-year-old was silently scored against the 60–64 data while being shown a "60–69" label — a real mismatch between what the UI implied and what was actually measured. Fixed to the full 7-band table and a raw-age input, matching the Balance and VO2max checks' pattern.)*

3. **Result labels (verbatim, `en.ts` `assess.sitToStand.result`):**
   - `below` → "Below typical range for your age group"
   - `within` → "Within typical range for your age group"
   - `above` → "Above typical range for your age group"

   (Note: `sitToStand.ts` itself also hardcodes these same three label/title/text strings inside `interpretSitToStand()`, but the page only reads `result.status` from that function and pulls the displayed label/title/text from `en.ts` — the `.ts` file's own strings are computed but unused for display. They match `en.ts` verbatim, so no conflict, just dead duplication worth knowing about.)

4. **Scoring direction:** Higher = better (more reps = stronger).

5. **Citation string displayed:** "Rikli & Jones Senior Fitness Test" (via `typicalRange(lo, hi)`: *"Typical range for your group: {lo}–{hi} stands (illustrative reference, Rikli & Jones Senior Fitness Test)."*) — no year given anywhere in the displayed string. The file header comment doesn't add a year either. **Year: MISSING.**

6. **Disclaimer (verbatim):** "This is an educational screening check, not a diagnosis. If you felt very unsteady during this test, please mention it to your doctor."

## 2. Balance Check

**Source files:** `lib/assessments/balance.ts`, `app/assess/balance/page.tsx`, `lib/i18n/en.ts` (`assess.balance`)

1. **Raw measure:** `time` — seconds balanced on one leg, eyes open, one decimal place. Hard cap: `TIME_CAP = 60` (test stops at 60s).

2. **Cut-off table (as coded, `BALANCE_NORMS` — mean ± 1 SD, clamped to `[0, 60]`):**

   | Sex | Age band | Mean (s) | SD | Computed range (s), clamped 0–60 |
   |---|---|---|---|---|
   | Male | 65–69 | 51.0 | 9.8 | 41.2–60.0 |
   | Male | 70–74 | 48.8 | 12.2 | 36.6–60.0 |
   | Male | 75–79 | 42.3 | 16.8 | 25.5–59.1 |
   | Male | 80–84 | 32.5 | 20.2 | 12.3–52.7 |
   | Male | 85+ | 23.6 | 21.9 | 1.7–45.5 |
   | Female | 65–69 | 50.1 | 10.7 | 39.4–60.0 |
   | Female | 70–74 | 46.1 | 15.0 | 31.1–60.0 |
   | Female | 75–79 | 38.1 | 18.8 | 19.3–56.9 |
   | Female | 80–84 | 26.9 | 20.8 | 6.1–47.7 |
   | Female | 85+ | 17.3 | 19.4 | 0–36.7 (clamped from a negative lower bound) |

   `ageBand()`: `<70`→"65-69", `<75`→"70-74", `<80`→"75-79", `<85`→"80-84", else "85+". Result is `below` if `time < lo`, `above` if `time > hi`, else `typical`.

   The source study covers ages 65+ only — no 50–64 data exists. As with Sit-to-Stand, ages 50–64 are deliberately scored against the youngest real band (65–69) rather than left unscored or given invented numbers; the age input in `app/assess/balance/page.tsx` is floored at 50 to match.

   **Extra coded threshold not in `balance.ts` — lives in `app/assess/balance/page.tsx` line 373:** if `answers.time < 5`, a separate fall-risk warning renders regardless of the age/sex band result above. This is a real, coded cutoff that sits outside the interpret function.

3. **Result labels (verbatim, `en.ts` `assess.balance.result`):**
   - `below` → "Below typical range for your age group"
   - `typical` → "Typical for your age group"
   - `above` → "Above typical range for your age group"

   Plus the separate `<5s` flag: heading `doctorFlag` = "⚠️ Worth mentioning to your doctor", body `doctorFlagBody` = "Holding a one-leg stance for less than 5 seconds has been linked to a significantly higher risk of injurious falls (Vellas et al., 1997). This is a signal worth following up on, not a diagnosis."

4. **Scoring direction:** Higher = better (longer hold = stronger balance).

5. **Citation strings:**
   - Main norms, displayed: "Seino et al., 2014" (via `typicalRange`: *"Typical range for your age & sex: {lo}–{hi}s (illustrative reference, Seino et al., 2014)."*)
   - Main norms, full form (code comment only, not displayed): "Seino S, Shinkai S, Fujiwara Y, et al. PLOS ONE. 2014;9(6):e99487 (pooled analysis of 4,683 community-dwelling older Japanese adults)."
   - Fall-risk flag, displayed and matching the comment: "Vellas et al., 1997" / comment gives full form "Vellas B, et al. J Am Geriatr Soc. 1997;45(6):735–738."

6. **Disclaimer (verbatim):** "This is an educational screening check, not a diagnosis. If you felt very unsteady during this test, please mention it to your doctor and consider having someone nearby next time."

## 3. VO2 Max & Resting Heart Rate

**Source files:** `lib/assessments/vo2max.ts`, `lib/i18n/en.ts` (`assess.vo2max`)

1. **Raw measure collected:** `rhr` — resting heart rate, beats per minute (60-second manual pulse count), plus `age`. These two inputs feed a **computed** value, not a directly measured one:
   - `hrMax = round(208 − 0.7 × age)`
   - `vo2max = round(15.3 × (hrMax ÷ rhr) × 10) / 10` — i.e. mL/kg/min, rounded to 1 decimal.
   No cap/clamp is applied to either formula in code.

2. **Cut-off table (as coded, `VO2_NORMS`; six ascending bands per sex/age cell, each defined by an upper bound; band = first one the value is `<`):**

   | Sex | Age band | Poor < | Fair < | Average < | Good < | Excellent < | Superior (≥ Excellent max) |
   |---|---|---|---|---|---|---|---|
   | Male | 50–59 | 20.9 | 27.1 | 39.7 | 45.6 | 50.7 | ≥50.7 |
   | Male | 60–69 | 17.4 | 23.7 | 34.5 | 40.3 | 43.0 | ≥43.0 |
   | Male | 70–79 | 16.3 | 20.4 | 30.4 | 36.6 | 39.7 | ≥39.7 |
   | Female | 50–59 | 16.0 | 19.9 | 27.6 | 32.0 | 35.9 | ≥35.9 |
   | Female | 60–69 | 13.4 | 17.2 | 23.8 | 27.0 | 29.4 | ≥29.4 |
   | Female | 70–79 | 13.1 | 15.6 | 20.8 | 23.1 | 24.1 | ≥24.1 |

   Age banding is coded exactly as: `<60` → "50-59" table, `<70` → "60-69", else → "70-79". Per an explicit code comment, anyone 80+ is scored on the 70–79 table — "not fixing this, faithfulness to the original instrument is the point." Unlike Sit-to-Stand and Balance, a real 50–59 band exists in this source, so no youngest-band substitution is needed here. The age input in `app/assess/vo2max/page.tsx` is floored at 50 (tightened from 18, which previously let anyone as young as 18 be scored on the 50–59 table with no real basis for that either).

3. **Result labels (verbatim, `en.ts` `assess.vo2max.category`, matches `vo2max.ts` exactly):**
   - `poor` → "Poor for your age & sex"
   - `fair` → "Fair for your age & sex"
   - `average` → "Average for your age & sex"
   - `good` → "Good for your age & sex"
   - `excellent` → "Excellent for your age & sex"
   - `superior` → "Superior for your age & sex"

   (The narrative result block collapses these six into three text variants — `low` covers poor+fair, `average` stands alone, `high` covers good+excellent+superior — but the *label* shown for the number itself is always one of the six above.)

4. **Scoring direction:** Higher = better (higher estimated VO2max = fitter).

5. **Citation strings displayed:**
   - "Mandsager et al., JAMA Network Open, 2018" — general VO2max/mortality claim (intro).
   - "Uth et al., 2004" — Heart Rate Ratio Method (intro2). Full form in code comment: "Uth et al., Eur J Appl Physiol, 2004."
   - "Cooper Institute / ACSM norms" — attributed for the category table itself (via `estimateFor(age, sex)`).

   **Conflict/gap:** the `hrMax` formula (`208 − 0.7 × age`) is the Tanaka formula. The code's header comment attributes it explicitly — *"HRmax via Tanaka, Monahan & Seals (2001)"* — but this citation is **never shown to the user**; none of the displayed `en.ts` strings mention Tanaka, Monahan, Seals, or 2001. The formula is fully displayed-and-used; its citation is code-comment-only.

6. **Disclaimer (verbatim):** "This is a formula-based estimate, not a lab measurement — individual accuracy varies, and it tends to underestimate VO2 max in fitter people. It's a screening tool, not a diagnosis. Always check with your doctor before starting a new exercise programme."

## 4. Nutrition & Protein Check

**Source files:** `lib/assessments/nutritionProtein.ts`, `lib/i18n/en.ts` (`assess.nutritionProtein`)

1. **Raw measure:** Sum of 8 frequency items (`fish, poultry, redmeat, eggs, tofu, dairy, legumes, nuts`), each scored 0–4 (Never=0, 1–2x/week=1, 3–4x/week=2, 5–6x/week=3, Daily+=4). Score range **0–32**. A separate "usual portion size" question is collected but explicitly **not included in the score** (code comment: "portion is shown separately, not included in the score").

2. **Cut-off table (as coded, `interpretProteinScore`, no age/sex split):**

   | Score | Band |
   |---|---|
   | 0–10 | `elevated` |
   | 11–20 | `watch` |
   | 21–32 | `good` |

3. **Result labels (verbatim, `en.ts` `assess.nutritionProtein.result`, matches `.ts` exactly):**
   - `elevated` → "Low frequency"
   - `watch` → "Moderate frequency"
   - `good` → "Good frequency"

4. **Scoring direction:** Higher = better (more frequent protein-source intake = better).

5. **Citation string:** **Conflict.** The code comment cites two sources: *"adapted from the Protein Screener 55+ (Wijnhoven et al., PLOS ONE, 2018), a validated Dutch tool, using Singapore-relevant food items per Whitton, Ho, Rebello & van Dam (Public Health Nutrition, 2018)."* Neither author name nor year appears anywhere in the displayed `en.ts` copy — `intro2` only says: *"Adapted from the Protein Screener 55+ (a validated Dutch tool) using food items confirmed relevant to Singapore's multi-ethnic diet."* The formal citations exist only in the source comment, not in the app UI.

   Separately, `proageing-site/nutrition.html`'s own marketing copy **does** display "Whitton et al. 2018" and "Wijnhoven" — so the site shows the citation the app's code was ported from, but the app itself dropped it from the user-facing text.

6. **Disclaimer (verbatim):** "This is an informational screening tool, not a diagnosis. For a precise measurement of your protein intake, ask your doctor for a referral to a dietitian."

## 5. Sleep Quality Check (PSQI)

**Source files:** `lib/assessments/sleepQuality.ts`, `lib/i18n/en.ts` (`assess.sleepQuality`)

1. **Raw measure:** Full Pittsburgh Sleep Quality Index (PSQI) global score, computed from bed/wake time, sleep latency, sleep hours, 8 disturbance items (Q5a–Q5i, Q5j write-in intentionally excluded from scoring per the official rule for a blank/no-comment item), overall quality rating, medication use, and two daytime-dysfunction items. Each of the 7 components (C1–C7) is scored 0–3; **global score range 0–21**. Sleep efficiency is also computed (`sleepHours ÷ hoursInBed × 100`, capped at 100%) and displayed, but efficiency itself only feeds into deriving C4 — it is not part of the headline score beyond that.

2. **Cut-off table (as coded, `interpretPSQI`, no age/sex split — this is the standard global PSQI cutoff, not a Singapore-adapted one):**

   | Total (0–21) | Band |
   |---|---|
   | 0–5 | `good` |
   | 6–21 | `poor` |

   Component sub-scoring rules (all as coded, no age/sex split):
   - **C1** (quality) = raw Q6 answer (0–3).
   - **C2** (latency): `q2new` from minutes-to-fall-asleep (`≤15`→0, `≤30`→1, `≤60`→2, else 3) + Q5a (0–3), summed then re-banded: sum=0→0, `≤2`→1, `≤4`→2, else 3.
   - **C3** (duration): sleep hours `≥7`→0, `≥6`→1, `≥5`→2, else 3.
   - **C4** (efficiency): `≥85%`→0, `≥75%`→1, `≥65%`→2, else 3.
   - **C5** (disturbances): sum of Q5b–Q5i (8 items, Q5j excluded): 0→0, `≤9`→1, `≤18`→2, else 3.
   - **C6** (medication use) = raw Q7 answer (0–3).
   - **C7** (daytime dysfunction): Q8+Q9 summed: 0→0, `≤2`→1, `≤4`→2, else 3.

3. **Result labels (verbatim, `en.ts` `assess.sleepQuality.result`, matches `.ts` exactly):**
   - `good` → "Good sleep quality"
   - `poor` → "Poor sleep quality"

4. **Scoring direction: Lower = better.** This is the one check in the set where a higher raw number is the worse outcome — displayed explicitly as "PSQI global score (0–21, lower is better)".

5. **Citation string displayed:** "Buysse et al., 1989" (via `cutoff(efficiency)`: *"A score of 5 or below is associated with good sleep quality; above 5 is associated with poor sleep quality (Buysse et al., 1989)."*) — matches the code comment's "Pittsburgh Sleep Quality Index (PSQI; Buysse et al., 1989)." No conflict.

6. **Disclaimer (verbatim):** "This is a wellness screening tool based on a published research questionnaire, not a medical diagnosis. If sleep problems are affecting your daily life, it's worth discussing with your doctor."

## 6. Connection Check (LSNS-6 + UCLA-3)

**Source files:** `lib/assessments/connection.ts`, `lib/i18n/en.ts` (`assess.connection`)

1. **Raw measure:** Two instruments combined:
   - LSNS-6 family/friends network — 3 items each (0–5 scale: None=0 … Nine or more=5), summed into `family` (0–15) and `friends` (0–15) separately.
   - UCLA-3 loneliness — 3 items (1–3 scale: Hardly ever=1, Some of the time=2, Often=3), summed into `loneliness` (**3–9**, not 0-based).

2. **Cut-off table (as coded, no age/sex split):**

   | Measure | Cutoff | Label |
   |---|---|---|
   | Family/friends network score | `< 6` | `isolated` |
   | Family/friends network score | `≥ 6` | `connected` |
   | Loneliness (UCLA-3) total | `≤ 3` | `good` ("Not lonely") |
   | Loneliness (UCLA-3) total | `4–5` | `watch` ("Somewhat lonely") |
   | Loneliness (UCLA-3) total | `≥ 6` | `elevated` ("Lonely") |

   Code comment states explicitly these thresholds (network `<6`, loneliness `≥6`) are **not** the original LSNS-6/UCLA-3 Western norms — they are Singapore-sample-specific values reported in Ge, Yap & Heng, *BMC Geriatrics* 2022 (606 community-dwelling older adults), chosen because that study found loneliness, not network size alone, predicted frailty risk.

3. **Result labels (verbatim):**
   - Network flag (`en.ts`): `isolated` → "Isolated", `connected` → "Connected"
   - Loneliness (`en.ts` `assess.connection.result`, matches `.ts` exactly): `good` → "Not lonely", `watch` → "Somewhat lonely", `elevated` → "Lonely"

4. **Scoring direction:** Mixed within the same check. Network score: higher = better (more connections). Loneliness score: **lower = better** (higher = more lonely) — reverse-scored relative to the network half.

5. **Citation strings:** **Conflict/gap.** Code comment cites the instruments' original sources — "Lubben Social Network Scale (LSNS-6; Lubben et al., The Gerontologist, 2006)" and "UCLA-3 Loneliness Scale" (no author/year given for UCLA-3 anywhere in the codebase — **MISSING**) — and the Singapore-threshold source "Ge, Yap & Heng, BMC Geriatrics 2022."
   - Displayed `en.ts` copy (`intro1`) names "the Lubben Social Network Scale (LSNS-6)" and "the UCLA-3 Loneliness Scale" **without** the Lubben et al. 2006 citation attached — that citation exists only in the code comment, not in the UI.
   - `intro2` does display the Singapore-study citation, but as "(Ge, Yap & Heng, BMC Geriatrics)" — the year (2022) appears earlier in the same sentence ("In a 2022 Singapore study…") rather than inside the citation parenthetical itself.
   - `proageing-site/connection.html`'s marketing copy, by contrast, displays "Lubben et al. 2006" directly — so again, the site shows a citation the app's own UI omits.

6. **Disclaimer (verbatim):** "This is a research-based screening tool, not a diagnosis. If persistent loneliness is affecting your wellbeing, please talk to your doctor or a counsellor."

## 7. Cognitive Decline Risk Check (SLAS Risk Index)

**Source files:** `lib/assessments/cognitiveDecline.ts`, `lib/i18n/en.ts` (`assess.cognitiveDecline`)

1. **Raw measure:** A 10-item weighted checklist summed into a single **risk index score, range 0–13**:
   - Age: Under 65=0, 65–74=1, 75+=2 (max 2)
   - Sex: Male=0, Female=1 (max 1)
   - Education: Secondary+=0, Primary/none=3 (max 3)
   - Depression (treated or ≥5 symptoms): No=0, Yes=1 (max 1)
   - Life satisfaction (not very satisfied): No=0, Yes=1 (max 1)
   - Hearing problems: No=0, Yes=2 (max 2)
   - Cardio-metabolic count (waist, glucose, BP, lipids — count of "Yes" answers out of 4): `0` → 0 pts, `1–2` → 2 pts, `≥3` → 3 pts (max 3)

2. **Cut-off table (as coded, `interpretSLASScore`; band thresholds are flat — not further split by age/sex, even though age and sex are themselves scored input components):**

   | Total (0–13) | Band |
   |---|---|
   | 0–5 | `good` |
   | 6–7 | `watch` |
   | 8–13 | `elevated` |

3. **Result labels (verbatim, `en.ts` `assess.cognitiveDecline.result`, matches `.ts` exactly):**
   - `good` → "Below the screening threshold"
   - `watch` → "At the screening threshold"
   - `elevated` → "Above the screening threshold"

4. **Scoring direction: Lower = better** (lower score = lower predicted risk).

5. **Citation string displayed:** "Ng et al., 2021" (intro1). Full form, code comment only: "Ng TP, Lee TS, Lim WS, et al. J Prev Alzheimers Dis. 2021;8(3):335–344." Consistent (abbreviated in UI, full in comment) — not a conflict.

6. **Disclaimer (verbatim):** "This is a research-based screening tool, not a diagnosis. Only a doctor can assess memory or thinking changes properly — please share this result with yours, especially if your score is 6 or higher."

## 8. Family History: Know Your Risk

**Source files:** `lib/assessments/familyHistory.ts`, `lib/i18n/en.ts` (`assess.familyHistory`)

**This check does not produce a single score.** It produces one categorical flag per category (`cvd`, `cancer`, `neuro`, `metabolic`), each independently `none` / `present` / `elevated`, plus a summary count of how many of the 4 categories are flagged and how many are `elevated`.

1. **Raw measure:** Per category — whether a first-degree relative was diagnosed (`has: boolean`), and at what age (`age: number | null`), plus the respondent's own sex (used only for the CVD threshold). Cancer additionally captures cancer type (`breast | colorectal | ovarian | other`), how many relatives were diagnosed (`relativeCount: "one" | "twoOrMore"`), and — only asked when `relativeCount` is `"twoOrMore"` — whether they're on the same side of the family (`sameSide: boolean`).

2. **Cut-off table (as coded, one threshold per category):**

   | Category | Threshold for `elevated` | Note |
   |---|---|---|
   | Cardiovascular disease | Age < 50 (male) / Age < 60 (female) | Defaults to the stricter (male, <50) threshold if sex is unanswered |
   | Cancer — colorectal | Age ≤ 60, **or** 2+ relatives with the same cancer on one side of the family | Screening start age if age-elevated: `min(40, age − 10)`, interval 5 years; if not elevated: start 50, interval 10 years. The same-side cluster route bypasses this age-based schedule entirely — see cluster note below |
   | Cancer — breast | Age ≤ 60, **or** 2+ relatives with the same cancer on one side of the family | |
   | Cancer — ovarian/other | Age ≤ 60, **or** 2+ relatives with the same cancer on one side of the family | |
   | Neurological (Alzheimer's/dementia/Parkinson's) | Age < 65 | |
   | Metabolic (diabetes/obesity/metabolic syndrome) | Age < 35 | Note: this is the only category where the non-`elevated` positive case is still `present`, not `none` — *any* family history of diabetes is flagged as `present` regardless of age, per MOH guidance treating it as a risk factor "regardless of the age they were diagnosed" |

   No age/sex split beyond the CVD category's own male/female threshold — age/sex are not used as a demographic lens on the results the way they are in Sit-to-Stand, Balance, or VO2max; age here is compared directly against a fixed per-category number, and sex only selects which fixed CVD number to use.

   **Same-side cluster (cancer only, added 2026-08-05):** 2 or more relatives with the *same* cancer, both on the *same side* of the family (both maternal or both paternal), is treated as `elevated` independent of age at diagnosis — this is a separate, age-independent trigger, not a modifier of the age threshold above. It only fires when age alone doesn't already qualify (`computeCancer`'s `cluster` check is gated on `!early`), so the existing per-type early/late copy always stays accurate to what it claims. One relative on each side does **not** count as a cluster — CDC, NCCN, and Singapore's NCCS all frame their genetic-counselling referral criteria around same-side clustering specifically, because these cancers are common enough to appear in unrelated relatives by chance, and a single-gene mutation (BRCA1/2, Lynch/MMR) is inherited from one parent, not both. This distinction did not exist before 2026-08-05 — the check only ever asked "has a first-degree relative been diagnosed", with no side-of-family or relative-count captured, so a real cluster and two unrelated diagnoses looked identical on paper. Cardiovascular, neurological, and metabolic disease do **not** get an equivalent same-side field: they're polygenic/multifactorial conditions, and their own source guidelines (NCEP ATP III for CVD; standard T2D and Alzheimer's risk literature) score by relative count alone, regardless of side — see the sources doc for the research supporting this (maternal transmission shows a measurably stronger association for both diabetes and Alzheimer's, but neither has been formalized into a same-side screening rule the way hereditary cancer syndromes have).

3. **Result labels (verbatim, `en.ts` `assess.familyHistory.flags`):**
   - `none` → "No flag"
   - `present` → "Family history"
   - `elevated` → "Elevated" (changed from "Elevated — early onset" on 2026-08-05 — the label can no longer claim age, since the cancer category's same-side cluster route reaches `elevated` without an early-onset age)

4. **Scoring direction:** Not applicable — categorical flags, not a directional score. `none` is the favourable state; `present`/`elevated` are risk flags.

5. **Citation string:** **No academic citation string exists for this check** — by design. Each category result carries a `source` tag instead of an author/year citation: `"🇸🇬 Singapore MOH"` (CVD, colorectal cancer, metabolic), `"🌐 International (mixed evidence)"` (breast cancer), `"🌐 International (NCCN)"` (other cancer), `"🌐 International"` (neuro), `"🌐 International (CDC, NCCN) · 🇸🇬 NCCS Singapore"` (cancer same-side cluster). One next-step string for early breast cancer does cite a study inline: "recent research (BCSC, 2022) questions applying this uniformly, especially for relatives diagnosed 35–45" — but this is advisory copy, not the basis for the elevated/present cutoff itself.

6. **Disclaimer (verbatim):** "This is an informational screening tool, not a diagnosis. Only a doctor can properly assess your personal and family risk — please share these answers with them, especially for any category flagged above."

## 9. Sense of Purpose Check (Ikigai-9)

**Source files:** `lib/assessments/purpose.ts`, `lib/i18n/en.ts` (`assess.purpose`)

1. **Raw measure:** 9 items, each on a 1–5 agreement scale (Strongly disagree=1 … Strongly agree=5), across three 3-item subscales (`feelings`, `future`, `meaning`, each 3–15). No reverse-scored items (per code comment). **Total range 9–45.**

2. **Cut-off table (as coded, `interpretIkigaiScore`, no age/sex split):**

   | Total (9–45) | Band |
   |---|---|
   | 9–20 | `low` |
   | 21–32 | `mid` |
   | 33–45 | `high` |

   `en.ts` itself explicitly flags these as non-clinical: *"Illustrative bands only: 9–20 lower, 21–32 moderate, 33–45 strong — not official clinical cutoffs."* This qualifier is additional to, and distinct from, the check's general disclaimer below.

3. **Result labels (verbatim, `en.ts` `assess.purpose.result`, matches `.ts` exactly):**
   - `low` → "Lower sense of ikigai right now"
   - `mid` → "Moderate sense of ikigai"
   - `high` → "Strong sense of ikigai"

4. **Scoring direction:** Higher = better (higher score = stronger sense of purpose).

5. **Citation strings displayed:**
   - "Imai, Osada & Nishi, 2012" — the Ikigai-9 instrument itself (intro1).
   - "Ohsaki study, Sone et al., 2008" — supporting evidence linking ikigai to lower mortality risk (intro2), a second, separate citation from the instrument's own source.

6. **Disclaimer (verbatim):** "This is a wellness reflection tool based on a published research questionnaire, not a mental health diagnosis. If you're feeling persistently low, hopeless, or unmotivated, please reach out to your doctor or a counsellor — support helps."

# Part 2 — Tools (not checks)

Added 2026-08-17, same method as Part 1: read out of the code, nothing
inferred, `MISSING` where the code does not state a value.

**Why these are in a separate part.** The nine above are *checks*: they measure
something about the person and compare it to a population norm, which is what
"norms" means in Part 1. The two below are *tools*: they compute a target from
what you tell them. There is no norm to compare against and no saved result —
`lib/tools.ts` keeps them deliberately outside `ASSESSMENT_TYPES` so the
Longevity Profile can keep saying "9 of 9 checks" truthfully.

So for a tool, the equivalent of a cut-off table is **the formula and its
evidence base**, plus any lookup values the formula consumes. That is what is
recorded here.

---

## 10. Training Zone Finder (tool)

**Source files:** `lib/assessments/trainingZone.ts`, `app/assess/training-zone/page.tsx`, `lib/i18n/en.ts` (`assess.trainingZone`)

1. **Raw measure collected:** `age` only — a stepper/number input, **clamped 18–100** in `app/assess/training-zone/page.tsx`, defaulting to 60 and falling back to 60 on unparseable input. Nothing else is asked. Sex is not collected and does not enter the formula.

2. **Computed values (`computeTrainingZone`, no cut-off table — a formula, not a band lookup):**
   - `hrMax = round(208 − 0.7 × age)`
   - `zoneLow = round(hrMax × 0.64)`
   - `zoneHigh = round(hrMax × 0.76)`

   No clamp is applied to any of the three outputs. Worked example, verified in-browser: age 60 → hrMax 166, Zone 2 106–126 bpm.

3. **Result labels (verbatim, `en.ts`):** `maxHr` → "Max heart rate (bpm)"; `zoneRange` → "Zone 2 range (bpm)". No banding, no category, no better/worse — the output is two numbers and a range, which is the whole point of it not being a check.

4. **Scoring direction:** Not applicable. There is no good or bad result; it is a target to aim at.

5. **Citation strings displayed:**
   - `intro1` — "…using the age-predicted heart rate formula from Tanaka, Monahan & Seals (2001)."
   - `sources` — "Max heart rate estimated using the Tanaka formula — Tanaka H, Monahan KD, Seals DR. J Am Coll Cardiol, 2001."

   **Consistency note, and a fix to Part 1's flagged gap.** §3 (VO2 Max) records that the Tanaka attribution existed only as a code comment and was never shown. This tool displays it twice, in full journal form. The two features share the identical `208 − 0.7 × age` formula by explicit design — the code comment says *"Same formula the VO2 max check already uses for its own max-HR figure, so the two checks can't disagree about the same person"* — so a user who runs both sees the same hrMax from both, which is the intended behaviour rather than a coincidence.

   **`MISSING`: the 64–76% Zone 2 bounds have no displayed citation.** The code comment attributes them — *"Zone 2 is 64–76% of max HR: the moderate band in the ACSM's classification"* — but no displayed string names ACSM or any source for the percentages. The formula that produces hrMax is cited; the percentages that turn it into a training zone are not. This is the same class of gap as the one §3 flagged and fixed for Tanaka, one level down.

6. **Safety copy (verbatim):**
   - `medicationNote` — "If you take a heart-rate-affecting medication (such as a beta blocker), these estimates won't apply to you — ask your doctor for your target range instead."
   - `disclaimer` — "This is an educational estimate, not a diagnosis. Always check with your doctor before starting a new exercise programme, especially if you have a heart condition or take medication that affects your heart rate."

7. **Storage:** none. Nothing is written to Supabase or `localStorage`.

## 11. Protein Calculator (tool)

**Source files:** `lib/assessments/proteinCalculator.ts`, `app/assess/protein-calculator/page.tsx`, `lib/i18n/en.ts` (`assess.proteinCalculator`)

1. **Raw measures collected:** `weightKg` — stepper/number input **clamped 30–200**, default 60, falling back to 60 on unparseable input. Plus `doesStrengthWork` — a yes/no on "Do you do strength exercise twice a week or more?". Age is **not** collected, despite the advice being age-motivated; the target is weight-driven only.

2. **Rate table (as coded, `PROTEIN_PER_KG` — g of protein per kg of body weight per day):**

   | Band | Condition | Low | High |
   |---|---|---|---|
   | `base` | No regular strength work | 1.0 | 1.2 |
   | `active` | Strength exercise 2×/week or more | 1.2 | 1.5 |

   `computeProteinTarget` returns `low = round(weight × band.low)`, `high = round(weight × band.high)`, and `perMeal = round(low / 3)`. Worked examples, verified in-browser: 70 kg base → 70–84 g/day, 23 g per meal; 70 kg active → 84–105 g/day.

   The three-meal divisor is a code-comment decision, not a sourced one: *"Three meals is the split the programme already teaches, and lands near the 25–30g per sitting that the muscle-synthesis research points to."* **`MISSING`: no citation is displayed or named in code for the 25–30 g per-sitting figure**, and `perMeal` is derived from `low` only, so it under-states the per-meal figure for anyone aiming at the top of their range.

3. **Food lookup table (as coded, `PROTEIN_FOODS` — 19 items, 11 everyday + 8 hawker; grams are whole numbers and live in code so the two languages cannot drift, with only labels translated):**

   | Key | Label (`en.ts`) | Grams | Group |
   |---|---|---|---|
   | `egg` | Egg | 7 | everyday |
   | `tauKwa` | Tau kwa, 1 piece | 12 | everyday |
   | `softTofu` | Soft tofu, 1 block | 8 | everyday |
   | `greekYoghurt` | Greek yoghurt, small tub | 15 | everyday |
   | `milk` | Milk, 1 glass | 8 | everyday |
   | `soyaMilk` | Unsweetened soya milk, 1 glass | 7 | everyday |
   | `peanuts` | Peanuts, small handful | 7 | everyday |
   | `wholemealBread` | Wholemeal bread, 2 slices | 8 | everyday |
   | `fishPalm` | Fish, palm-sized | 22 | everyday |
   | `chickenPalm` | Chicken breast, palm-sized | 30 | everyday |
   | `dhal` | Dhal, 1 bowl | 9 | everyday |
   | `fishSoup` | Fish soup | 25 | hawker |
   | `chickenRice` | Chicken rice — breast, less rice | 30 | hawker |
   | `yongTauFoo` | Yong tau foo — 6 items with egg | 28 | hawker |
   | `fishBeeHoon` | Sliced fish bee hoon soup | 28 | hawker |
   | `economyRice` | Economy rice — meat, egg, tofu, veg | 30 | hawker |
   | `leiCha` | Thunder tea rice (lei cha) | 20 | hawker |
   | `thosaiDhal` | Thosai + dhal + egg | 20 | hawker |
   | `wantonMee` | Wanton noodle soup | 22 | hawker |

   All 19 keys resolve to a label in `en.ts`; none is missing. `tallyTotal` is a plain sum of `count × grams` over these plus any user-added items.

   > **`MISSING` — and the most substantive gap in this document.** **None of these 19 gram values has a source, anywhere.** Not displayed, not in a code comment, not in `PROAGE_ASSESSMENT_SOURCES.docx`. The code comment says only *"Foods someone here actually eats, with protein rounded to whole grams… Figures are typical servings, not precise ones."* The displayed `sources` string cites PROT-AGE and ESPEN, but those are the source for the **target**, not for the food figures.
   >
   > This matters more than an ordinary citation gap. The target says a 70 kg person needs 70–84 g; these 19 numbers are what tells them whether they got there. An unsourced food table is the part a dietitian would question first, and the part that decides whether the tool's advice is actually followed. The natural authority is Singapore's Health Promotion Board food composition data — but it is **not** currently cited, and nothing in the code says the values came from there.

4. **User-added items (`makeCustomFood`):** a free-text label **truncated to 40 characters** (`CUSTOM_NAME_MAX`) and grams **clamped 1–100** (`CUSTOM_GRAMS_MAX`), rounded. Falls back to a localised "Something else" label when the name is blank. These carry no source by definition — the user supplies the figure.

5. **Scoring direction:** Higher tally = closer to target. Progress is measured against `target.low`, so `remaining = max(0, low − total)` and the bar fills against the **bottom** of the range; reaching `low` shows "Target reached" even though `high` is not met.

6. **Citation strings displayed (verbatim):**
   - `sources` — "Targets follow PROT-AGE (Bauer et al., 2013) and ESPEN (Deutz et al., 2014) for healthy older adults."
   - Code comment expands both to full form: "Bauer et al., JAMDA 2013" and "Deutz et al., Clinical Nutrition 2014". The journal names are **not** displayed, unlike VO2 max's Uth and Tanaka strings which give full journal form. Minor inconsistency in citation depth between features.
   - `palmNote` — "25g is roughly a palm-sized piece of fish, chicken or tofu." **`MISSING`: unsourced.**

7. **Safety copy (verbatim):**
   - `kidneyWarning` — "If you have kidney disease, do not use this target — a higher protein intake can be harmful, and your doctor should set your figure instead." Shown unconditionally on the results screen, in coral. This is the only contraindication warning in either tool and is load-bearing: the whole point of the tool is to raise protein intake above the general RDA.
   - `disclaimer` — "These are estimates for healthy adults, not a prescription. Portions vary a lot between stalls and kitchens, so treat the totals as a guide rather than a measurement."

8. **Storage:** `localStorage` only, never Supabase. `proage-protein-target` holds `weightKg`, `doesStrengthWork` and any custom foods; `proage-protein-tally` holds `{date, counts}` and is discarded on load if `date` is not today. Both are filtered on read rather than trusted — a non-numeric `weightKg` or a custom food with a non-finite `grams` is dropped, because either would corrupt every total silently.
